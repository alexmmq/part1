<h1>CustomThreadPoolExecutor</h1> 
<h2>1. Анализ производительности</h2>
<p>Кастомный пул потоков CustomThreadPoolExecutor был разработан с целью обеспечить высокую гибкость и 
производительность при работе с различными типами задач. В качестве объекта сравнения выступает стандартный 
ThreadPoolExecutor</p>
<h5>Сравнение с ThreadPoolExecutor</h5>
Гибкость конфигурации:  CustomThreadPoolExecutor предоставляет расширенные возможности настройки, 
такие как поддержка минимальной численности резервных потоков (minSpareThreads) и более гибкое управление 
временем жизни неиспользуемых потоков (keepAliveTime). Это позволяет лучше адаптироваться к специфическим требованиям 
приложений.
Производительность: в тестовых сценариях наш пул показал сопоставимую производительность с ThreadPoolExecutor 
при средней и низкой нагрузке. 
Однако наша реализация может быть более эффективной при высоких нагрузках благодаря использованию нескольких очередей 
и алгоритму балансировки на основе наименьшей загруженности (Least Loaded).


<h2>2. Важные параметры и их влияние на работу</h2>
<h6>Core Pool Size</h6> 
Высокое значение corePoolSize уменьшает задержку при старте выполнения задач, 
но увеличивает потребление памяти и ресурсы процессора.
Низкое значение corePoolSize экономит ресурсы, но может привести к увеличению времени ожидания выполнения задач.
<h6>Maximum Pool Size</h6>
Увеличение maxPoolSize позволяет обрабатывать большее количество одновременных задач, но требует большего объема 
оперативной памяти и вычислительных мощностей.
Поддержание низкого значения maxPoolSize полезно для предотвращения перегрузки системы, 
но может ограничить пропускную способность при пиковых нагрузках.
<h6>Keep Alive Time</h6>
Более длительное время жизни неиспользованных потоков (keepAliveTime) может снизить затраты на создание новых потоков, 
но увеличит объем потребляемых ресурсов.
Сокращение keepAliveTime позволяет быстрее освобождать ресурсы, но может увеличить задержки при повторном запуске задач.
Работа keepAliveTime основывается на алгоритме метода poll, задающего TimeOut для задачи из BlockingQueue.
<h6>Queue Size</h6>
Большой размер очереди (queueSize) предотвращает потерю задач, но может замедлить реакцию системы на новые запросы.
Маленький размер очереди ускоряет реагирование на новые задачи, но может приводить к частым отказам при пиковых 
нагрузках.
<h5>Рекомендации по настройкам</h5>
Средняя нагрузка: Установить corePoolSize и maxPoolSize равными друг другу, чтобы минимизировать задержки при 
старте задач. Использовать умеренный размер очереди и короткое время жизни неиспользуемых потоков.
Высокая нагрузка: Увеличить maxPoolSize для поддержки большого количества одновременных задач. 
Необходимо увеличить размер очереди, чтобы предотвратить потери задач, а также необходимо установить умеренное 
время жизни неиспользуемых потоков.
Низкая нагрузка: Уменьшить corePoolSize и maxPoolSize, чтобы экономить ресурсы. 
Использовать короткий keepAliveTime и небольшой размер очереди.
<h5>Принцип действия механизма распределения задач</h5>
Механизм распределения задач в нашем пуле основан на принципе наименьшей загруженности (Least Loaded). Мы использовали несколько очередей, каждую из которых связали с отдельным рабочим потоком. При поступлении новой задачи выбирается наименее загруженная очередь, что позволяет равномерно распределять нагрузку между потоками и избегать ситуаций, когда некоторые потоки перегружены, а другие простаивают.
Алгоритм балансировки действует следующим образом:

Когда новая задача поступает в пул, определяется очередь с наименьшим количеством ожидающих задач.
Задача добавляется в эту очередь, и соответствующий рабочий поток приступает к её выполнению.
Если все очереди заняты, создается новый поток (при условии, что общее количество потоков не превышает maxPoolSize).
Такой подход обеспечивает эффективное использование ресурсов и снижает вероятность возникновения узких мест в системе 
при условии использования CustomThreadPoolExecutor.
